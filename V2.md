# QFlux V2 Upgrade Specification

## Purpose

Upgrade the current browser MVP into a reliable quantum learning laboratory without breaking the existing static demo.

The current MVP is intentionally simple:

- Static HTML, CSS, and JavaScript.
- Three qubits and eight circuit steps.
- Client-side state-vector simulation.
- H, X, Y, Z, S, T, and adjacent CNOT gates.
- Bell, superposition, and GHZ templates.
- Measurement histogram, amplitudes, reduced Bloch vectors, and JSON export.

V2 must turn these capabilities into a maintainable product with a tested simulation core, a richer circuit model, scalable rendering, and clear educational feedback.

## V2 Product Goals

1. Let a learner create, inspect, save, and replay circuits without setup.
2. Make state evolution understandable, not just numerically correct.
3. Support useful educational algorithms and multi-qubit gates.
4. Keep the simulator deterministic when a seed is supplied.
5. Preserve a fully client-side fallback for zero-cost hosting.
6. Keep the UI responsive on modest hardware.
7. Make every exported circuit portable and versioned.

## Non-Goals

- Real quantum hardware execution in V2.
- Fault-tolerant error-correction research.
- More than 15 qubits in the exact state-vector mode.
- A general-purpose replacement for Qiskit or Cirq.
- A backend requirement for the core user workflow.

## Feature Scope

### P0: Required for V2

#### Circuit editor

- Variable qubit count from 1 to 15, with a warning above 10.
- Variable circuit depth with add/remove time steps.
- Click-to-place gates, drag-and-drop placement, move, copy, and delete.
- Multi-cell gate placement for controlled and multi-target gates.
- Wire labels, step labels, selection state, keyboard navigation, and undo/redo.
- Validation errors for invalid controls, duplicate targets, and overlapping operations.
- Zoom and horizontal scrolling without changing cell dimensions.
- Clear circuit and reset to `|0...0>`.

#### Gate library

Support these gates with explicit target/control metadata:

- Single-qubit: I, X, Y, Z, H, S, Sdg, T, Tdg.
- Parameterized: RX, RY, RZ, U3.
- Controlled: CX/CNOT, CZ, CY, CRX, CRY, CRZ.
- Multi-qubit: SWAP, Toffoli/CCX.
- Measurement and barrier operations.
- Custom 2x2 unitary gate only after matrix validation.

Every gate must declare its arity, parameter schema, display label, unitary behavior, and inverse behavior where applicable.

#### Simulation

- Exact state-vector simulation for 1-15 qubits.
- Correct arbitrary control and target ordering.
- Gate-by-gate execution trace.
- Final state vector and basis-state probabilities.
- Measurement shots with optional seed.
- Normalization checks after every operation in development mode.
- Clear numerical error handling for invalid or unstable input.

#### Inspection

- Amplitude table with basis labels, real/imaginary values, phase, and probability.
- Probability histogram with sort and threshold controls.
- Per-qubit reduced density matrix and Bloch vector.
- Optional state-at-step playback.
- Circuit summary: qubits, depth, gate count, estimated memory, and runtime.

#### Persistence and export

- Save/load versioned circuit JSON.
- Import validation with useful error messages.
- OpenQASM 3 export for supported gates.
- Download simulation results as JSON and CSV.
- Local browser autosave with an explicit clear-data action.

### P1: Learning and algorithm features

- Algorithm template library:
  - Bell state.
  - GHZ state.
  - Equal superposition.
  - Deutsch-Jozsa.
  - Bernstein-Vazirani.
  - Grover search for 2-4 qubits.
  - Quantum teleportation.
  - Superdense coding.
  - QFT and inverse QFT.
  - Small toy factoring example, clearly labelled educational only.
- Step-through mode with play, pause, next, previous, and reset.
- Plain-language explanation for each selected gate.
- Algorithm annotations showing expected result and why it works.
- Searchable gate and template library.
- Shareable URL or encoded circuit payload, with no account required.

### P2: Advanced analysis

- Noise models: bit flip, phase flip, depolarizing, amplitude damping, and readout noise.
- Density matrix mode for mixed states.
- Entanglement entropy for a selected bipartition.
- Concurrence for two-qubit states.
- Stabilizer-style metadata for supported Clifford circuits.
- Optional Web Worker or WASM acceleration.
- Optional Python/FastAPI reference engine for development cross-validation.

## Architecture Rules

### Rule 1: Keep the engine independent from the UI

The quantum engine must not access the DOM, browser APIs, React, Zustand, or charting libraries. It receives typed circuit data and returns typed results.

Recommended boundary:

```text
CircuitDocument -> Simulator -> SimulationResult
```

The UI may format results, but it must never implement gate math.

### Rule 2: Use a canonical circuit document

Do not store gates as strings in a 2D grid. The grid is a view. The source of truth is a versioned document:

```ts
interface CircuitDocument {
  schemaVersion: 2;
  id: string;
  name: string;
  numQubits: number;
  depth: number;
  gates: GateOperation[];
  metadata?: {
    description?: string;
    template?: string;
    createdAt?: string;
    updatedAt?: string;
  };
}

interface GateOperation {
  id: string;
  type: GateType;
  step: number;
  targets: number[];
  controls?: number[];
  params?: Record<string, number>;
  condition?: ClassicalCondition;
}
```

All imported documents must be migrated by schema version before use.

### Rule 3: Validate before simulation

Use one validator for editor actions, imports, API requests, and tests. Reject:

- Qubit indices outside the document range.
- Negative or out-of-range steps.
- Duplicate targets or controls.
- A target also listed as a control.
- Missing parameters or parameters outside documented bounds.
- Unsupported gate combinations.
- Overlapping operations that cannot execute in the same step.
- Circuit sizes above the configured hard limit.

Never silently drop invalid operations.

### Rule 4: Use sparse local gate application

Do not build a full $2^n x 2^n$ matrix for ordinary gates. Apply local gates directly to the state vector using index masks and permutations. Full matrix expansion is allowed only in a test helper for small circuits.

Use `Float64Array` pairs or a typed complex representation for predictable memory use. Avoid allocating object-heavy complex numbers inside hot loops.

### Rule 5: Preserve qubit ordering everywhere

Use little-endian basis indexing:

- Qubit 0 is the least-significant bit.
- Basis index `3` in a 3-qubit system is `|011>`.
- Exporters, labels, measurement results, Bloch vectors, and tests must use the same convention.

The convention must be displayed in the UI and covered by tests.

### Rule 6: Make simulation results immutable

A simulation request returns a new result object. The editor may change the circuit without mutating a previous result. Results should include a circuit revision or hash so stale responses cannot overwrite newer results.

### Rule 7: Separate exact simulation from sampling

The simulator produces exact amplitudes and probabilities. Measurement sampling consumes those probabilities and never mutates the state unless collapse is explicitly requested. A seeded sampler must reproduce the same histogram.

### Rule 8: Keep rendering bounded

Do not render all 32,768 basis states by default for a 15-qubit circuit. Use:

- Probability thresholding.
- Top-N results.
- Search by basis label.
- Virtualized lists for large result sets.
- A visible count of hidden states.

### Rule 9: Prefer progressive enhancement

The static client-only engine remains the fallback. A worker, WASM engine, or Python service may accelerate simulation, but the UI must have one engine interface and should not care which implementation is active.

```ts
interface QuantumEngine {
  simulate(circuit: CircuitDocument, options?: SimulationOptions): Promise<SimulationResult>;
  measure(result: SimulationResult, options: MeasurementOptions): MeasurementResult;
}
```

### Rule 10: No hidden numerical behavior

Use a shared tolerance, for example `1e-10`, for normalization and equality checks. Display rounded values only at the presentation layer. Keep raw values available for export and tests.

### Rule 11: Accessibility is part of correctness

- Every control has an accessible name.
- Gate buttons expose gate name and parameters.
- The circuit grid supports keyboard placement and focus indication.
- Color is never the only state indicator.
- Reduced-motion mode disables decorative animation.
- Results are available as text, not only canvas or WebGL pixels.

### Rule 12: Keep educational explanations next to behavior

Each gate and algorithm template must have a short explanation, required inputs, expected output, and a link to the relevant result view. Explanations must not claim that a measurement is deterministic when it is probabilistic.

## API and Engine Contracts

### Simulation options

```ts
interface SimulationOptions {
  maxQubits?: number;
  captureSteps?: boolean;
  normalize?: boolean;
  noise?: NoiseConfig;
}
```

### Simulation result

```ts
interface SimulationResult {
  schemaVersion: 2;
  circuitRevision: string;
  stateVector: ComplexNumber[];
  probabilities: number[];
  blochVectors: Record<number, [number, number, number]>;
  stepStates?: ComplexNumber[][];
  metrics: {
    norm: number;
    runtimeMs: number;
    memoryBytes: number;
  };
  warnings: string[];
}
```

### Measurement result

```ts
interface MeasurementResult {
  shots: number;
  seed?: number;
  counts: Record<string, number>;
  probabilities: Record<string, number>;
}
```

If a FastAPI service is added, keep these JSON contracts identical to the client engine. REST is for complete simulation and export. WebSocket is only for step streaming and must have a REST fallback.

## State Engine Design

1. Initialize `state[0] = 1` and all other amplitudes to zero.
2. Apply each operation in ascending step order.
3. Within one step, reject operations that overlap on a qubit.
4. Apply single-qubit gates with pairwise index updates.
5. Apply controlled gates with bit masks and target permutations.
6. Apply SWAP and Toffoli as dedicated permutation operations.
7. Compute probabilities as squared magnitudes.
8. Check norm against tolerance in development and test builds.
9. Compute reduced density matrices by partial trace, then Bloch vectors from Pauli expectations.
10. Return raw values and diagnostics; formatting belongs to the UI.

Do not use Qiskit or another external simulator as a runtime dependency. Use one optionally in development to cross-check reference circuits.

## Performance Budgets

- 1-10 qubits: simulate common circuits in under 100 ms on a typical laptop.
- 11-15 qubits: simulate common circuits in under 500 ms where memory permits.
- UI interactions must remain responsive while simulation runs in a Worker.
- Never block the main thread for a large circuit.
- Warn before operations likely to allocate more than 256 MB.
- Cancel stale worker jobs when a newer circuit revision is submitted.

## Testing Requirements

### Unit tests

- Complex arithmetic and tolerance behavior.
- Every fixed gate matrix.
- RX, RY, RZ, and U3 parameter edge cases.
- Single-qubit application on every qubit position.
- CNOT with every valid control-target direction.
- CZ, SWAP, and Toffoli.
- Normalization after random valid circuits.
- Partial trace and Bloch vectors for `|0>`, `|1>`, `|+>`, `|+i>`, Bell, and GHZ states.
- Measurement with fixed seeds.
- JSON schema validation and migration.

### Integration tests

- Bell state has probabilities 0.5 at `|000>` and `|011>` under the current little-endian convention.
- Three-qubit superposition has probability 1/8 for all basis states.
- GHZ has equal probability at `|000>` and `|111>`.
- Teleportation reproduces the input state on the destination qubit after corrections.
- Grover amplifies the selected item for supported sizes.
- Export then import produces an equivalent circuit.
- OpenQASM export is accepted by a reference parser.

### Browser tests

- Load app with no console errors.
- Place, move, delete, undo, and redo a gate.
- Change qubit count and circuit depth.
- Run, measure, inspect, save, load, and export.
- Verify keyboard operation and accessible names.
- Verify mobile layout and horizontal circuit scrolling.

## Upgrade Sequence

### Phase 1: Stabilize the current MVP

- Add tests around the existing Bell, superposition, and GHZ behavior.
- Extract the math from `app.js` into a small engine module.
- Replace silent invalid CNOT behavior with validation errors.
- Add schema version to export JSON.
- Add a deterministic measurement seed option for tests.

### Phase 2: Introduce the domain model

- Add `CircuitDocument` and `GateOperation` types.
- Write migration from the current row/step representation.
- Add centralized gate registry and validation.
- Add undo/redo history based on immutable circuit revisions.

### Phase 3: Move heavy work off the UI thread

- Add a Web Worker engine adapter.
- Keep the synchronous engine for tests and small circuits.
- Add progress, cancellation, runtime, and memory diagnostics.

### Phase 4: Upgrade the interface

- Migrate to Vite + React + TypeScript only after the engine contracts are stable.
- Use a state store for document, selection, history, and result state.
- Add keyboard-accessible circuit editing.
- Add virtualized result lists and responsive layout.

### Phase 5: Add education and interoperability

- Add algorithm templates and explanations.
- Add step playback.
- Add JSON schema validation, CSV export, and OpenQASM 3 export.
- Add shareable circuit links.

### Phase 6: Add advanced analysis

- Add noise and density-matrix mode behind explicit UI controls.
- Add entanglement metrics.
- Add optional Python reference service only if client performance requires it.

## Definition of Done for V2

V2 is complete when:

- A user can create a 1-15 qubit circuit with supported single, controlled, and multi-qubit gates.
- Invalid circuits are blocked with understandable messages.
- The same circuit produces the same seeded measurement result across runs.
- The engine passes all reference-circuit tests and preserves qubit ordering.
- The UI remains responsive for supported circuit sizes.
- Circuit JSON can be saved, loaded, migrated, and exported.
- OpenQASM export works for every supported gate or clearly reports unsupported operations.
- Bell, GHZ, Grover, and teleportation have verified templates.
- The static client-only path still works when no backend is available.
- The app has no console errors in a clean browser session.

## Release Guardrails

- Do not merge UI features without engine tests.
- Do not increase the qubit limit without a memory estimate and performance test.
- Do not add a gate without a registry entry, validator, simulator implementation, export behavior, and tests.
- Do not silently change basis ordering or JSON schema.
- Do not introduce a backend until the same behavior works through the client engine.
- Keep user data local by default and document every network request.
